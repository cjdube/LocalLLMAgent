# LocalLLMAgent codebase analysis

## 1. What this project does

LocalLLMAgent is a single-user, local-first personal AI system for a Mac mini. Its interactive agent, Wren, is served by Ollama by default and is reachable through a Flask web chat over Tailscale; Wren can answer from the user's calendar, wiki, memory, mail, tasks, and other services and can take actions through confirmation-gated tools. Its second agent, ScribeJay, runs unattended journaling pipelines that turn activity from sources such as Chrome, YouTube, Strava, mail, Git, and calendar events into calendar records and Obsidian pages that Wren later reads. macOS `launchd` keeps the chat server alive and runs scheduled jobs, JSON files under `config/` hold local state, and an explicit per-task backend setting can opt selected work into Gemini instead of the local model.

## 2. Overall architecture

The codebase is organized around two agents sharing a small substrate:

- **Wren, the interactive/read-and-act agent.** `chat/server.py` owns the Flask application, authentication, in-memory conversations, context compaction, cancellation, frontier escalation, and confirmation continuations. The page at `chat/static/index.html` supplies the chat DOM, while `chat/static/chat-dock.js` owns the browser interaction and rendering. Feature-specific HTTP APIs live in `chat/routes_*.py` blueprints; read-only dashboard aggregation lives in `chat/insights.py`.
- **The model seam.** `agent/loop.py` defines the canonical message and tool-call protocol. `advance()` is the resumable tool-calling state machine used by chat and background work; `resolve()` appends an approved or declined result for a call on which `advance()` paused; `complete_text()` is the one-shot, tool-free path used when deterministic Python owns the surrounding document. `_llm_chat()` selects a backend, `_ollama_chat()` implements the local streaming transport, and `agent/backends/gemini.py` translates the same canonical shapes to and from Gemini.
- **Capabilities and policy.** Each capability is a plain Python module in `agent/tools/` with a schema and callable where it is model-facing. `agent/toolset.py` is the integration point: `TOOLS` contains schemas, `DISPATCH` maps schema names to callables, `CORE_TOOL_NAMES` and `TOOL_GROUP_NAMES` decide which schemas enter the small model's context, and `WRITE_TOOLS`, `CONSEQUENTIAL_TOOLS`, `UNATTENDED_EXCLUDED_TOOLS`, `confirm_set_for()`, and `excluded_for()` encode the execution boundary. `chat/server.py` and `tasks/bg_worker.py` both consume this registry rather than defining separate agent capabilities.
- **Local state.** Capability modules persist JSON under `config/` through `agent/store.py`. `locked()` holds an inter-process lock over an entire read-modify-write cycle, `load_json()` degrades a corrupt file to an empty default after quarantining it, and `atomic_write_json()` uses same-directory temporary files plus `os.replace()` so readers never observe a partial document.
- **Unattended Wren work.** Entry points in `tasks/` expose `main() -> int` functions and use `tasks/_common.py:setup_logger()` and `notify_failure()`. `launchd/local.wren.*.plist` files invoke them on calendar or polling schedules. Most deterministic digest jobs use `agent.loop.complete_text()` only for bounded prose; `tasks/bg_worker.py` is the exception that reuses `advance()` and `resolve()` for user-created background jobs, persisting a pause when an action needs phone approval.
- **ScribeJay, the journaling/write-the-record agent.** Modules in `scribejay/` follow gather → optional `complete_text()` → write. For example, `scribejay/daily_chrome_learnings.py:main()` calls `fetch_chrome_history()`, compacts the result with `agent.activity_log.compact_sites()`, asks `complete_text()` for a template-shaped draft, then calls `persist_or_email()`. ScribeJay never calls `advance()` and never imports `agent.toolset` or `chat`; `scribejay/__init__.py` defines the narrow shared-module “porch.” `scribejay/model.py:backend()` gives it an independent `SCRIBEJAY_*` backend chain.

The central relationship is therefore: **ScribeJay writes the record; Wren reads it and acts on request.** Both share model transport, selected data-access modules, logging helpers, and locked storage, but only Wren receives a tool registry. `launchd` drives both families of entry points; the dashboard reconstructs their run state from the start/complete/error lines in their log files.

## 3. End-to-end trace of a key press

This project is a browser-based chat app, not a terminal UI, so no terminal emulator or terminal input class participates in a key press. The closest project-owned end-to-end path is pressing Enter in the running chat page. Ordinary character keys only trigger `chat/static/chat-dock.js:autoGrow()` through the textarea's `input` listener; Enter without a modifier sends the turn.

1. **The page establishes the DOM contract.** `chat/static/index.html` defines `#messages`, the `#composer` form, the `#input` textarea, and the `#send` button, then loads `chat/static/chat-dock.js`. There are no UI classes in this path; the script is an IIFE containing plain functions.
2. **Enter becomes a submit event.** The `keydown` listener on `input` in `chat/static/chat-dock.js` checks for `e.key === "Enter"` with no Shift, Ctrl, or Meta modifier, calls `preventDefault()`, and invokes `form.requestSubmit()` (falling back to `sendBtn.click()`). Shift+Enter and Ctrl/Cmd+Enter remain newline input.
3. **The browser updates immediately.** The form's `submit` listener prevents navigation, reads and trims `input.value`, calls `addMessage("user", message)` to create a `.msg.user` element using `textContent`, resets the textarea, calls `setBusy(true)` to disable input and turn Send into Stop, and adds the animated `.typing` element with `addTyping()`.
4. **The browser sends JSON.** `postTurn("/chat", {message}, typingEl)` calls `fetch()` with `POST`, `Content-Type: application/json`, and the serialized message. Flask routes the request to `chat/server.py:chat()`; `chat.auth._authenticated()` rejects unauthenticated sessions.
5. **The server admits one turn for the session.** `chat()` validates the message and obtains a UUID-backed session id from `_session_id()`. `_begin_turn()` atomically installs a `threading.Event` in `cancel_events` under `_turn_registry_lock`; a concurrent turn for the same session receives HTTP 409. If configured, `agent.loop.probe_local_model()` first checks Ollama's single request slot and may return a `busy` response before history is touched.
6. **The server constructs model context.** `chat()` retrieves the session's list from `conversations`, declines any abandoned `pending_confirmations` with `agent.loop.resolve()`, rebuilds the system message through `_system_message_content()`, and folds the durable-in-session summary into it with `_with_summary()`. `_trim_history()` removes only whole old user turns; `_summarize_dropped()` uses `complete_text()` to update `summaries`. `agent.toolset.groups_for_message()` keyword-preloads relevant deferred tool groups, then the user message is appended to history.
7. **The shared turn runner enters the agent loop.** `chat.server._run_turn()` builds the live schema list with `agent.toolset.tools_for()`, binds the session-aware `load_tools` implementation from `_make_load_tools()`, and calls `agent.loop.advance(history, tools, dispatch, confirm_before=WRITE_TOOLS, stateful_tools=WRITE_TOOLS, should_cancel=cancel.is_set, ...)`.
8. **The backend receives a canonical chat request.** `advance()` calls `agent.loop._llm_chat()`. With the default backend, `_llm_chat()` calls `_ollama_chat()`, which posts the messages, live tool schemas, context size, and generation cap to Ollama's `/api/chat` endpoint with streaming enabled. `_ollama_chat()` concatenates content chunks, collects streamed `tool_calls`, and checks `should_cancel()` between chunks; the Stop button reaches `chat.server.chat_cancel()`, which sets the same `threading.Event` and causes `TurnCancelled` to unwind the request.
9. **Tool calls either run or pause.** `advance()` appends the assistant message. If it contains no tool calls, it returns `{"type": "final", "text": ...}`. For an ordinary allowed call, `_execute_tool_call()` looks up the name in the provided `dispatch` map, calls the capability function with the model's arguments, caps and JSON-serializes its result, and appends a `role: "tool"` message carrying `tool_name`; `advance()` then calls the model again. Duplicate calls and total iterations are bounded in code. If a call's name is in `WRITE_TOOLS`, `advance()` returns `{"type": "confirm", "call": ...}` without executing it.
10. **The Flask result is shaped and history is kept coherent.** `_run_turn()` stores a paused call in `pending_confirmations` and formats its human-readable preview with `agent.toolset.describe_call()` and `describe_call_detail()`. A final answer goes through `_call_response()`. Cancellation or an exception deletes history back to the pre-turn checkpoint; a successful turn stays in `conversations`. The per-session turn event is removed in `finally`, releasing the one-turn slot.
11. **The browser replaces the activity indicator with the result.** `postTurn()` parses the response and calls `handleResult()`, which removes the typing element. A `final` response goes through `renderFinal()` and then `addMessage("wren", result.text)`, creating a `.msg.wren` element with `textContent`, appending it to `#messages`, scrolling, and calling `setBusy(false)`. A `confirm` response instead calls `addConfirm()`; Confirm or Cancel posts to `chat.server.chat_confirm()`, which calls `agent.loop.resolve()` and then `_run_turn()` to continue the same model turn. `busy`, `cancelled`, and error responses have parallel explicit rendering branches.

The tests mirror the seams in this trace: `tests/chat-dock.test.js` covers Enter, submit, final rendering, cancellation, and confirmation; `tests/test_server.py` covers history compaction, one-turn admission, rollback, and continuation; `tests/test_loop.py` covers stream reassembly, cancellation, dispatch, duplicate suppression, backend translation, and `resolve()`.

## 4. Three complex or risky areas

### 1. Chat session and continuation state (`chat/server.py`)

This is the highest-coupling module in the interactive path. A session is spread across `conversations`, `summaries`, `pending_confirmations`, `pending_backends`, `loaded_groups`, `cancel_events`, and `_session_last_active`; those structures must move together across `/chat`, `/chat/confirm`, `/chat/escalate`, `/chat/cancel`, `/chat/new`, and idle eviction. Checkpoint placement is semantic: a failed new turn must roll back its user message, while a failed confirmation continuation must preserve the resolved tool result so the preceding assistant call is not orphaned. Threaded Flask requests also share the cancellation registry and mutable histories. A change to trimming, escalation, cancellation, or confirmation can therefore produce malformed model history, duplicate execution, stuck UI state, privacy leakage to the wrong backend, or a session race without causing a simple syntax failure. The concentrated regression coverage in `tests/test_server.py` is part of the design, not optional scaffolding.

### 2. The backend-neutral tool state machine (`agent/loop.py` and `agent/backends/gemini.py`)

`advance()` has to preserve one protocol across Ollama streaming and Gemini's translated format while supporting cancellation, dynamically extended tool schemas, multiple calls in one assistant message, per-tool output caps, gated pauses, repeat suppression, state-changing writes followed by valid re-reads, a hard confirmation count, and a final no-tools recovery after the iteration limit. `resolve()` must append a result shaped so a decline is a terminal user decision rather than a retryable tool error. Small changes to message ordering, `tool_name`, argument normalization, or stop conditions can make the model repeat a consequential call, lose a tool result, or silently end with no answer. Because `chat/server.py` and `tasks/bg_worker.py` both resume this state machine at different times and through different approval surfaces, fixes must be verified through both callers.

### 3. Capability registration and the trust boundary (`agent/toolset.py`, `agent/tools/`, and `tasks/bg_worker.py`)

A model-facing capability is not complete when its Python function works. Its schema must enter `TOOLS`, its callable must enter `DISPATCH`, it must be placed in exactly one of `CORE_TOOL_NAMES` or `TOOL_GROUP_NAMES`, and it must be mapped to a service in `chat/insights.py:TOOL_SERVICES`. More importantly, the author must classify it in `WRITE_TOOLS`, `CONSEQUENTIAL_TOOLS`, and possibly `UNATTENDED_EXCLUDED_TOOLS`; mail-originated and ClickUp-originated jobs derive stricter gates through `confirm_set_for()` and removals through `excluded_for()`. That classification is security behavior: external content can contain prompt injection, and read-only calls with model-chosen URLs can still exfiltrate data. A registry edit can therefore make a tool unreachable, overload the local model's context, remove a confirmation barrier, expose persistent memory writes to unattended work, or create a misleading approval card. The partition, gating, describer, and dashboard drift-guard tests should be treated as required parts of any tool change.

## 5. Onboarding order

A new contributor should read `AGENTS.md` first for the invariants that bind changes, especially the Wren/ScribeJay seam, untrusted-content boundary, small-model constraints, test isolation rules, and registration checklists; then `README.md` for the product and operating model; then `docs/module-map.md` to choose the correct subsystem. For interactive work, continue with `chat/static/chat-dock.js`, the relevant route in `chat/server.py`, `agent/loop.py:advance()`/`resolve()`, `agent/toolset.py`, and one representative `agent/tools/*.py` module plus its flat test file. For journaling or scheduled work, read `docs/scribejay.md` and the porch in `scribejay/__init__.py`, then compare `scribejay/daily_chrome_learnings.py` and `tasks/morning_brief.py` with their launchd plists and tests. Read `docs/security-model.md`, `docs/model-constraints.md`, `docs/limits.md`, and `docs/timezones.md` before changing tool policy, model prompts, context budgets, web/API ingestion, or date handling.
